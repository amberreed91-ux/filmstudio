## 1. Executive verdict

**Conditionally verified — generic environment references have a verified *consumer* contract but no explicit, auditable *designation* contract.**

- The production **read** side of a generic environment anchor is real, enforced server-side, and covered by passing tests: identity provenance (canonical setting entity) + an approved, canonical, `kind=environment` registry row targeting that exact entity, resolved by `resolve_scene_reference_requirements`, frozen into the binding/contract, and re-verified downstream.
- The production **write** side of generic canonical status is **not implemented as an explicit creator operation**. The generic `canonical` flag can only become true through (a) the creator-sync path, which scopes environment rows to `target_id = scene_id` — a target identity that **no** production consumer accepts — or (b) a client-supplied `canonical: true` on the propose/confirm POST, which is **not** validated as an explicit designation.
- The reusable mechanism that *would* express explicit canonical authority already exists and is already wired end to end (Scene Direction `setting_reference_decision` on the approved storyboard version). It is generic in its **save** path but is only **consulted** for one exact project/setting pair in the resolve path.

No production-readiness claim is made. Studio is **not** declared production-ready.

## 5. Canonical-authority contract analysis

**Fields that establish authority**

| Property | Field(s) | Verified? |
|---|---|---|
| Identity | `ref_id` (PK), `image_url`, `kind='environment'` | Verified |
| Scope | `project_id` + `target_type='setting'` + `target_id` | Verified |
| Approval | `approval_state ∈ {candidate, approved, rejected}`, default `'approved'` (schema default) | Verified |
| Canonical status | `canonical` boolean, default 0 | Verified |
| Provenance | `source_kind`, `source_shot_id`, `category`, `created_at` | Verified |
| Designation audit | — | **Missing** (no actor/time/revision, no history) |

**Is designation a distinct operation?** Scene 002: yes. Generic: **no.** Two unintended promotion paths exist for generic rows:

1. `sync_creator_references` writes `canonical=True` directly as a side effect of syncing an approved Previs frame.
2. `ReferenceAssetService.confirm` persists the client-supplied model, and `ReferenceAsset` defaults `canonical: bool = False` but does not forbid `True`. `POST /{project_id}/reference-assets` therefore accepts a caller-declared canonical reference with no server-side designation step, no re-resolution against approved state, and no audit record. **Labelled as a risk; not reproduced by an executed test in this phase.**

**Can multiple canonical references exist for one target?** Yes — nothing enforces uniqueness:

- `_approved_setting_references` **collects every** row with `canonical` truthy, `approval_state=='approved'`, `kind=='environment'`, matching project/target (`reference_validation.py:329-360`); the same shape applies to `_approved_character_references`.
- `list_library` shows only `next(row for row in rows if canonical)` (first match) — so what the creator sees as "the canonical reference" and what production forwards can diverge when more than one row carries the flag.
- The Scene 002 storage setter changes only the selected row and explicitly declines to normalize competitors.

**Scope:** project-scoped and target-scoped (`target_type='setting'`, `target_id` = the canonical setting entity). Unrelated scenes/projects cannot inherit a reference: `_verify_setting_identity_provenance` enforces `entity.first_scene == scene_id` when set and `entity.project_id == project_id`, and `_approved_setting_references` filters on `project_id`/`target_id`.

**Revision safety / auditability:** the Scene Direction decision is revision-safe and auditable (new or changed decisions require the current approved storyboard version at save — Option B draft carry; an unchanged decision carries forward across current drafts and is re-validated live on every save, 422 if the referenced row is no longer approved and canonical; the persisted decision is re-read and byte-compared at reference-authorization time in `scene_production_pipeline_service.py:1725-1728`). The raw `canonical` flag itself is **not** revision-safe: no version pin, one row per boolean.

**Can a rejected/revoked/stale/unapproved reference remain usable?** Consumers require `approval_state=='approved'` **and** `canonical` truthy, and `update_reference_asset_state` blocks `rejected → approved`, so a rejected row cannot be selected through the reviewed paths. `sync_creator_references` never downgrades an approved/canonical row back to candidate (`reference_asset_service.py:839-857`), so a previously approved row keeps its flag — intended healing, but it also means a stale Previs frame can keep canonical status indefinitely (no staleness recompute for the flag). Exception risk: the `confirm` path in §5.1 above.

**Two incompatible target conventions (data-integrity finding).** `sync_creator_references` scopes environment rows to `target_id = scene_id`, while every consumer requires `target_id == <canonical setting entity id>`, and `resolve_canonical_setting_id` refuses `setting_id == scene_id`. Consequence (code-evidenced): a synced environment row **can satisfy no production setting gate**. It is nonetheless rendered in Reference Space as a distinct target's "Locked canonical" reference. The behavior is intentional-by-design in one narrow sense (the sync was written for the Scene 002 scene-scoped convention), but it produces a false canonical signal for generic projects. **Labelled Verified-by-inspection; not reproduced against a live project (boundary).**

## 8. Smallest recommended implementation slice

**Name:** *Explicit generic environment canonical designation (parameterized).*

**Expected behavior.** For any project/scene whose canonical setting entity resolves, the creator can explicitly designate one **already-approved** environment reference as that setting's canonical reference. The operation is server-authoritative, changes exactly one row's `canonical` flag, is rejected for candidates/unapproved/rejected rows, and never retargets or rewrites another row. Immediately after designation, the **existing, unmodified** generic consumer path (`_verify_setting_identity_provenance` + `_approved_setting_references`) becomes usable, so no resolve-path change is required for the slice to have value.

**Proposed API and service boundaries (reuse existing patterns; no new tables, no migration):**

- Storage: parameterized `set_setting_reference_canonical(*, ref_id, project_id, setting_id, canonical: bool)` mirroring `set_scene002_setting_reference_canonical` (`storage.py:14091`) but with `project_id`/`setting_id` as parameters instead of literals, and the same "update only the selected row" semantics.
- Service: `ReferenceAssetService.designate_setting_reference_canonical(project_id, setting_id, ref_id)` — resolve row, verify project/target/kind/approval, delegate to storage, re-read and return (the Scene 002 service method at `reference_asset_service.py:548` is the template; the Scene 002 ID gating is what gets parameterized, not removed).
- Route: a generic sibling to the existing Scene 002 setting-reference routes, e.g. `POST /{project_id}/setting-references/{setting_id}/{ref_id}/canonical` with `{"canonical": true}`, returning `{reference_asset: ...}` — following the existing `Literal`/scope-validation convention in `routes/reference_assets.py`. The Scene 002 routes stay exactly as they are.
- Read: expose the existing `canonical` flag through the already-existing library read (`list_library` / `list_assets`); no new read endpoint.

**Persistence implications:** none beyond the existing `reference_assets.canonical` column. No schema change, no migration, no new table.

**Fail-closed conditions (all must raise, not silently proceed):** unknown/foreign `ref_id`; `project_id` mismatch; `target_type != 'setting'`; `target_id != setting_id`; `kind != 'environment'`; `approval_state != 'approved'`; unusable/empty image URI; Scene 002 exact target routed through the legacy path (must continue to require its own lifecycle); storage write returning falsy.

**Regression tests (unit + API; no cross-boundary tests):**

1. Service: designate a generic `setting/<entity>` environment row → `canonical` true; a second row for the same target can also be designated, and the first row's flag is **not** silently cleared (documents the multiple-canonical reality rather than hiding it).
2. Service: designate fails closed for candidate, rejected, wrong-project, wrong-target, non-environment, and unknown ref_id — asserting the failure type, with no mutation.
3. API: route contract for success and each fail-closed case (including a foreign-project `project_id`).
4. **End-to-end consumption:** after designation, `resolve_scene_reference_requirements` for that generic project/scene returns the designated anchor in `allowed_urls` (extends the existing `test_deleted_supporting_upload_does_not_substitute_unrelated_references` fixture shape).
5. Scene 002 non-regression: existing `test_scene002_setting_reference_lifecycle.py` suite passes unchanged; the new generic route must not accept the Scene 002 exact target.

**Acceptance criteria.** (a) A generic setting with only candidate rows cannot be designated; (b) after one explicit designation, a generic scene resolves that anchor and rejects a different canonical/unapproved reference with `payload_canonical_reference_missing`/`stale_reference_payload` as applicable; (c) Scene 002 behavior and its 22 lifecycle tests are unchanged; (d) no new table/migration; (e) routes stay thin (service-mediated, no storage access in route bodies); (f) all new and existing focused suites pass.

**Explicitly out of scope for the slice:** consuming the Scene Direction decision generically, changing `sync_creator_references`' `target_id` convention, hardening the `confirm` endpoint's canonical field, and any uniqueness enforcement.
