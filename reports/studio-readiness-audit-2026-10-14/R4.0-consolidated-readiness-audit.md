## 7. Confirmation persistence and outcome traceability

- Confirmation (`ProductionDesk.tsx:385` `confirmed` state) is React in-memory only; the UI states it
  explicitly ("held for the upcoming submission, not yet durable", line 702). Handoff travels via
  route state (`confirmedBindingHandoff.ts`), which dies on reload/navigation; cross-project carriers
  are dropped. Reload → re-resolve + re-confirm. Safe (server re-verifies digests fail-closed) but
  non-durable — this is exactly the R4.2 problem; no schema exists for confirmations.
- Persisted per created job: input payload (frozen binding params), metadata (contract, manifest,
  fingerprints, digests, `router_execution` incl. the projection record + digest), output payload
  metadata. The outcome→binding→request link is durable for created jobs (integration-asserted);
  confirmations that never become jobs leave no trace (by design). No migration exists; R4.2 must
  decide whether confirmation persistence reuses job metadata shape or needs a new table.

## 10. Recommended next step

**Do not begin multi-shot design.** The single decision blocking it is the over-capacity binding policy
(§9.1): until an explicit rule exists for bindings above Router capacity, all-or-nothing batch
pre-authorization cannot be specified — a batch of individually valid shots can still be collectively
undeliverable. Decide that rule first (narrowest unblocking decision), then start R4.1. R4.2
confirmation persistence can proceed in parallel as designed.
