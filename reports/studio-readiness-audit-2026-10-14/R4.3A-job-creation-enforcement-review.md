## 5. Evidence for each demonstrated gap

The keystone grep: outside tests, `generation_contract=` is passed **only**
by `scene_production_pipeline_service.py` (lines 445-446 generic, 2338/2363-64
protected; line 226 is `build_execution_contract`, not job creation). No
caller in §3 #4–18 passes it, and none can smuggle one (explicit kwarg, not
part of `parameters`). Therefore:

- **A (batch preflight bypass): confirmed as fact, not a vulnerability.**
  Non-pipeline callers skip preflight — but preflight's per-job substance
  (contract/binding/manifest/capacity/authority checks) is re-enforced at
  creation, submit, and adapter time for every job, and over-capacity
  bindings additionally fail closed at the adapter builder.
- **B (confirmation bypass): no demonstrated gap.** Persisted confirmation
  has meaning only for reference-bound `runway_router` shots; no
  non-pipeline caller can create one. There is no unconfirmed
  reference-bound production work outside the pipeline to protect.
- **C (creation-time bypass): none.** Universal gate in `create_job`
  (:2105+, :2612), now regression-locked (§8).
- **D (submit-time bypass): none.** `submit_job` → :4265 for every path
  including queue worker (:1002) and all retry/revision flows.
- **E (adapter-level bypass): none.** Dual enforcement (:1872, :2394) plus
  replay equality; direct `_submit_job_after_authorization` calls cannot skip
  the boundary check by design (comment at :2015).
- **F (untraceable jobs): none.** Pipeline jobs carry the R4.3
  `batch_authorization` stamp; non-pipeline jobs carry standard job metadata;
  router jobs exist only via the pipeline.

## 7. Decision and justification

**No implementation.** The condition for code change (Phase 3: a legitimate
production caller with a demonstrated enforcement gap) is not met — the
investigation proves the gap does not exist. The R4.3-D1 concern rested on
"a future batch entrypoint that creates jobs without preflight would bypass
R4.1A/R4.2"; the finding is stronger than a per-entrypoint audit: **no
entrypoint, present or future, can create a `runway_router` job without going
through the frozen-contract creation gate, and the only code that satisfies
that gate is the canonical pipeline.** Extending the confirmation flag to
non-pipeline callers would be dead code (their router requests fail before
reaching any confirmation check) and would falsely imply those paths can do
production router work. If a future caller ever passes
`generation_contract=`, that single grep-able kwarg is the tripwire for
re-opening this decision — documented here as the re-evaluation trigger.
