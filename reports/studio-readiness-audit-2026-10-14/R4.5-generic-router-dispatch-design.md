## 1. Root cause per gate (file:line, evidence level)

All four stops reject the same legitimate artifact: a pipeline-built multi-shot batch (two shots, each one approved character `face` reference + one canonical setting `environment` reference, 2 refs ≤ 4). Step 2c evidence is `R4.4-step2c-checkpoint-G-production-path.md` §3 plus the probe `studio-backend/tests/test_r44_step2c_production_path_probe.py` (asserts preconditions only; outcomes reported as JSON). ### Gate 1 — Preflight role allowlist (`scene_production_pipeline_service.py:804`, `:980-989`)

- What the code does: for generic `runway_router` entries, preflight parses the frozen contract (`FrozenGenerationContract.from_record`, `:975`), then rejects any frozen reference whose `studio_role` is not in `ROUTER_ROLES = {"reference", "storyboard", "storyboard_last"}` (`:804`, `:980-984`, code `unsupported_reference_role`, category `reference_authorization`, policy `v2`). Capacity is checked next (`:990-998`, `> ROUTER_CAPACITY`, imported at `:779` from the Runway projection).
- What the pipeline emits: `_approved_character_references` (`reference_validation.py:231`) emits character rows with `role`/`category` = `face` (also `general`, `full_body`); `_approved_setting_references` (`reference_validation.py:329`) emits setting rows with `role`/`category` = `environment`. `_canonical_binding_to_contract_references` (`scene_production_pipeline_service.py:35-45`) projects these into frozen contract references with `role="reference"` and `studio_role=<raw role>`, so `face`/`environment` survive into `studio_role` by design. The comment at `:35-45` documents this as intentional.
- Invariant the gate protects: the Router wire schema only accepts a closed role set; an unrepresentable studio role must fail closed before any job exists. **The invariant is legitimate.**
- Root cause: **the gate is too narrow, the upstream data shape is correct.** The gate compares the *studio* role against the *router* role set, but the existing codebase already defines the correct mapping: `normalize_studio_role` (`runway_reference_projection.py:150-168`) normalizes `face`/`general`/`alternate_angle`/`environment` → provider `reference`, `storyboard` → `first`, `storyboard_last` → `last`, and fails closed on anything else; `_SUPPORTED_STUDIO_ROLES` (`:85`) is exactly `{face, general, alternate_angle, environment}`; `_validate_v2_shape` (`:668-751`) enforces the same studio-role vocabulary for generic rows (character rows must be `face`/`general`/`alternate_angle`, setting row must be `environment`, `:_validate_v2_shape` at `:714-738`). Preflight ignores this mapping and demands the studio role already spell a router role. No pipeline-built contract with ordinary roles can pass.
- Evidence level: **Tested.** Step-2c probe: `preflight_ready=False`, both shots `unsupported_reference_role` / `reference_authorization` / policy `v2`; `generate_scene(provider="runway_router")` raises `ValidationError` (`batch_authorization_preflight_rejected`), 0 jobs, 0 transport calls.
- Related broken promise (Code-inspected): the comment at `:801-802` promises preflight "applies them to the same frozen artifact — never stricter than submission, only earlier." Submission itself *skips* these unprojected gates whenever a declared projection exists (`adapters/__init__.py:2269-2280` comment: "When a projection is declared … these unprojected gates do not apply"), but no generic job can ever declare one (§1.4). Preflight therefore mirrors the unprojected path unconditionally and is strictly stricter than the only submission path a generic job could take.

### Gate 2 — `create_job` contract-versus-manifest equality (`render.py:2468`, `:2518-2538`)

- What the code does: for `generation_contract is not None` (router-only, `:2418+`), `create_job` builds `expected_binding` (`:2468-2483`) from the frozen contract's canonical references with keys `ref_id, uri, target_type, target_id, role (= studio_role), category, canonical, approval_state, source_kind, [kind]` — **10 keys, no `project_id`** — then demands `manifest_entry.reference_binding == expected_binding` **and** `expected_binding == <same 10-key projection of `_frozen_reference_binding`>` (`:2517-2537`), else `ValueError("Frozen contract creative values do not match the manifest")` (`:2538`).
- What the pipeline emits: `build_shot_manifest` (`shot_manifest.py:159`) copies the **raw** binding rows verbatim (`[dict(row) for row in entry.reference_binding]`), `project_id` included; the raw setting row carries `"project_id": project_id` by construction (`reference_validation.py:350`, documented intentional). The contract side deliberately drops `project_id` (`:35-45`). The two canonical shapes therefore diverge by exactly one key on every setting-bearing shot.
- Contrast with the provider-neutral check just above (`:2338-2366`): `expected_manifest_reference_binding` includes `project_id` in its key tuple (`if key in row`, `:2341`) and compares against the manifest — which is why the `simulated` path is unaffected. The router-only block is the only place that drops the key.
- Invariant the gate protects: frozen contract, manifest row, and prepared binding must agree exactly — no silent substitution between freeze and persist. **The invariant is legitimate and must stay.**
- Root cause: **neither side is "wrong" in isolation; the coupling is the absence of a single defined comparison shape.** Two correct-per-their-layer shapes (raw-with-scope vs contract-without-scope) are compared with exact list-of-dicts equality at two different layers that each define their own projection inline. The gate is too narrow in *what it compares*, not in *that it compares*.
- Evidence level: **Tested.** Step-2c §3 diagnostic driving `create_job` directly with the same prepared entry: `binding_rows_carry_project_id=[false,true]`, `row_projection_equals_contract_projection=true`, `manifest_row_equals_contract_projection=false` → `:2538` raise.

### Gate 4 — `reference_projection_declaration_missing` (`adapters/__init__.py:2264`)

- What the code does: `_submit_job_after_authorization` first tries `_declared_reference_projection` (`adapters/__init__.py:1709-1828`). If no projection is declared (`PROJECTION_METADATA_KEY` and `AUTHORIZATION_METADATA_KEY` both absent) **and** `metadata.frozen_reference_binding is not None`, it fails closed with `reference_projection_declaration_missing` (`:2261-2266`). A generic authorization model must be designed (options in §3.4).

### `project_id` on setting rows — why it is there, what depends on it (§3d)

- Why it is there (Code-inspected): **setting authority / project scoping.** `_approved_setting_references` stamps `"project_id": project_id` (`reference_validation.py:350`); the Scene 002 authorization builder asserts `selected.project_id == project_id` and `row.project_id == project_id` (`scene_production_pipeline_service.py:2145-2163`); `reference_binding_for_requirements` and coverage preserve the rows verbatim. The key scopes the setting anchor to its owning project.
- What depends on it: the frozen-binding digest (`reference_binding_digest`, `reference_validation.py:378-382` — canonical JSON over the full rows, so the digest **covers** `project_id` wherever the digested list includes it); the provider-neutral creation check (`render.py:2338-2348`, includes the key); manifest verbatim-copy traceability (`shot_manifest.py:159`); the Scene 002 authorization equality (`approved_binding != binding`, `adapters/__init__.py:1759-1778`).
- What the router reconstruction compares and why: exact list-of-dicts equality between its 10-key contract projection and the persisted manifest row (`:782-783`), because the wire request must be lossless. The comparison is correct in intent; its projection omits a scoping key the manifest legitimately carries.
- Options (trade-offs, risks; recommendation in §3.4):
  1. **Include `project_id` in the router's expected projection.** Traceability: manifest and contract shapes converge; digest coverage unchanged. Security: preserves scoping only if the comparison also asserts the value equals the job's project (equality alone would accept a consistently-wrong project_id). Cost: touches provider + creation projections; stored frozen contracts unaffected (comparison-only change), but every existing hand-built test row without `project_id` must be re-examined.
  2. **Strip `project_id` at the projection layer** (manifest builder drops it, or contract projection drops it — the latter is already the case). Traceability: manifest loses the scoping key; downstream authority checks that read the manifest row lose their input. Security: weakens project scoping unless a separate explicit scope assertion is added at every gate. Not recommended as a bare strip.
  3. **Compare on a defined subset + separate explicit scope assertion (recommended).** Define one shared projection helper (comparison shape, e.g. the current 10 keys) used identically by `create_job`, reconstruction, and the parity test, **plus** an explicit `setting_row.project_id == job.project_id` assertion at creation and adapter time. Security: scoping is checked, not compared-away; traceability: manifest keeps the raw row, digest still covers the full row. No stored-contract change, no Scene 002 change.
- Confirmation required (§7): no option weakens project scoping or the frozen-binding digest **provided** option 3's separate scope assertion ships atomically with the subset comparison. Options 1-2 without that assertion would weaken scoping and are rejected.

## 3. Options per divergence, trade-offs, risks, recommendations

### 3.1 Role mapping: studio roles (`face`, `environment`, …) → router roles

- **R1 (recommended): preflight and unprojected submit/reconstruction gates check the *normalized provider role* via the existing `normalize_studio_role`, not the raw `studio_role`.** Where it lives: keep the mapping in `runway_reference_projection` (projection policy v2 owns role semantics today: `_SUPPORTED_STUDIO_ROLES`, `normalize_studio_role`, `_validate_v2_shape`); preflight, `create_job`'s router branch (if it gains a role check), the adapter unprojected path, and reconstruction all call it. Role semantics stay distinguishable as the brief requires (§9: face identity vs body, setting vs composition): `studio_role`/`category`/`target_type` remain the carried semantic fields; the provider role is a derived view used only for representability. Trade-offs: + single source of truth, + reuses Tested mapping, + `full_body`/`general` question surfaces explicitly (see owner decision §7.2); − touches four call sites atomically. Risks: low — behavior change is strictly widening toward already-authorized semantics, still fail-closed on unknown roles; negative controls (§5) pin the remaining rejections.
- **R2 (rejected): expand `ROUTER_ROLES` literals to include studio roles.** à la carte literals at each gate; duplicates semantics, drifts on the next role, no single owner. Rejected.
- **R3 (rejected): change the pipeline to emit `studio_role="reference"`.** Destroys the face-vs-body / setting-vs-composition distinction the brief requires and that v2 validation depends on. Rejected.

### 3.2 `project_id` comparison shape (see §1 analysis; recommended: option 3)

- **P1/P2/P3 as enumerated in §1.** Recommended: **P3 — one shared comparison-shape helper + explicit setting-scope assertion.** The helper (e.g. `contract_comparison_binding()` next to `_canonical_binding_to_contract_references`, or in `reference_validation`) returns the exact 10-key rows; `render.py:2468`, `runway_router_provider.py:744`, and the parity test import it — no more inline projections. The scope assertion (`setting row project_id == job/project_id`, plus digest coverage unchanged) ships in the same change at creation and adapter boundaries. Trade-offs: + manifest keeps raw traceability, + digest untouched, + scoping explicitly enforced rather than compared-away; − two-part change must land atomically (parity test enforces it). Risks: low-medium — the risk is landing the subset without the assertion (explicitly forbidden; §5 pins both).

### 3.3 Declared-projection requirement for generic projects

- **D1 (recommended): build a generic projection authorization for pipeline jobs.** Generalize the *record shape*, not the Scene 002 authority inputs: mint `reference_projection_authorization` for any pipeline-built router entry carrying `frozen_reference_binding` + frozen contract + persisted confirmation/digest evidence, binding `project_id/scene_id/shot_id/binding-digest/setting identity/capacity+roles verdict`. Reuse v2 shape validation + `normalize_studio_role` + `reference_binding_digest` + confirmation re-verification; do **not** reuse Scene 002's storyboard-version/asset-view specifics. The Scene 002 v1 path (`:1530` branch, `_build_reference_projection_authorization`, v1 suites) is untouched; generic jobs take a new adjacent branch. Trade-offs: + satisfies `:2264` through the designed declared path, + unprojected gates correctly skipped thereafter, + authorization semantics explicit and auditable; − new authority-minting code needs its own negative controls (§5). Risks: medium — this is the only option that mints new authority; §7.3 records it as an authorization-semantics decision requiring explicit owner approval. Alternatives:
- **D2 (rejected as primary): exempt small generic batches from the declaration requirement** (let ≤4 pipeline jobs fall through to direct reconstruction). Removes the very boundary that prevents unauthorized substitution; weakens the adapter invariant. Rejected — do not relax a check to make a test pass.
- **D3 (rejected): keep Scene-002-only declarations and route generic jobs through direct reconstruction with widened gates.** Leaves two submission paths with different authority properties and keeps preflight stricter-than-submit. Rejected.
