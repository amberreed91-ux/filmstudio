# R4.0A — Generic Projection Capacity Decision Brief

Date: 2026-10-14 · Branch: `backend-expansion-dependency-slicing` · HEAD: `86c1b58e`
Read-only. Nothing modified, staged, or committed; no providers called; no jobs created.

## 1. Executive recommendation

**Option C: explicitly reject bindings above the verified capacity, and keep enforcing 4 as the
ceiling — while recording that the external verification is stale and re-verifiable.**
The 4-limit is a code-embodied provider constraint with a dated verification claim
(docs + OpenAPI snapshot 2026-09-28), enforced at three independent layers. Independent web
re-verification this phase was **inconclusive** (router schema extractions truncated;
`model-routers.txt` 404), so the ceiling must neither be expanded on assumption nor treated as
eternally proven. The only invariant-preserving posture today is: enforce 4, reject above-4
fail-closed with the existing `invalid_canonical_count_or_shape` code, and close the one real gap —
the refusal currently surfaces at adapter submit time (job exists), not in batch preflight.

## 2. Current four-row limit and its actual origin

- **Provider API constraint (code-attributed):** `runway_router_provider.py:19-44` documents the
  "Authoritative API contract (verified against the official docs + the OpenAPI 3.1 spec generated
  from docs.dev.runwayml.com/openapi.json, 2026-09-28)": video `referenceImages (≤4, {uri, role:
  first|last|reference})`, encoded as `ROUTER_VIDEO_MAX_REFERENCE_IMAGES = 4` (:121, "Verified
  router input limits").
- **Enforced at three layers:** projection (`runway_reference_projection.py:128-133`
  `_assert_router_capacity`, plus v2's 1–4 shape rule and `policy_version_for_canonical_rows`);
  request builder (`runway_router_provider.py:640-647` and `:789` — over-limit raises before any
  network call); adapter replay (capacity equality on the record).
- **Not from:** Studio schema (no columnar limit), test fixtures (tests use 1–5 rows), or scene
  shape (requirements are unbounded — §3). The limit is a provider-side ceiling as embodied in code.

## 3. Supported generic-scene reference requirements

- Characters: `_approved_character_references` returns **all** approved canonical refs per focused
  character (face/general/alternate_angle, unbounded count);
  `reference_binding_for_requirements` (`reference_validation.py:402-412`) forwards all of them.
- Setting: exactly one anchor — exclusivity + `canonical_setting_reference_ambiguous` guard.
- Coverage (`scene_coverage_contract.py:632-647`) dedupes by ref_id but caps nothing.
- Every required row must be represented: provider module forbids dropping/substituting/reordering
  ("Approved references are forwarded as-is and in input order or the request fails"); coverage
  demands exact ordered agreement. **No permission exists to transform away a required row.**
- Consequence: the frozen binding **can** legitimately contain references v2 cannot represent
  (e.g. 2 characters × 2 refs + setting = 5). Per-shot character focus bounds this in practice, but
  nothing enforces ≤3 refs per character.

## 4. Verified provider and adapter constraints

- Verified in code (3 layers, §2): video referenceImages ≤4, roles first|last|reference, at most one
  first and one last (builder `:665-680`).
- Externally corroborated this phase: **nothing for the router schema** (inconclusive fetch).
  Counter-datapoint: Kling O3 *direct* image-to-video allows up to 7 references (model-specific
  schema, not the router schema — cannot be transferred).
- Composition conditioning (storyboard frames, first/last roles) travels separately from identity
  references and must not consume identity capacity (v1/v2 both forbid it) — corroborated in
  `freeze_generation_contract` and projection role gates.

## 6. Recommended contract and rejected alternatives

- **Retain:** ceiling 4, enforced at projection + builder; `invalid_canonical_count_or_shape` for
  0/6+ rows and v2's >4; v1 exact-five unchanged; all digest/fingerprint/authorization/
  materialization checks mandatory; multi-shot preflight must validate every shot binding before
  creating any job.
- **Reject A:** no evidence supports router acceptance above 4; expanding would weaken two gates.
- **Reject B as a capacity measure:** roles cannot manufacture capacity; identity/composition
  separation must stand.

## 7. Remaining unknowns and evidence needed

1. **Router acceptance above 4** — resolvable without live spend: an authorized `dryRun: true`
   probe with 5 referenceImages (dry runs bill nothing and return the routing decision). Requires
   credentials + explicit authorization; not performed here.
2. **Whether the 2026-09-28 verification claim is still current** — same probe doubles as a
   re-verification; alternatively re-fetch the router OpenAPI schema with a capable fetcher.
3. **Over-capacity UX** — product decision for a later phase: how creators narrow rich bindings
   (per-shot focus enforcement? designation caps? explicit deselection with re-freeze?).
