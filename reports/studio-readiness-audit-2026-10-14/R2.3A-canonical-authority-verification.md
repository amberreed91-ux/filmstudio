## 5. Sequential versus concurrent uniqueness (concern B)

- **Sequential uniqueness: proven by tests.** `test_designation_is_exclusive_and_clears_competing_canonical_anchor` and the ambiguity-then-designate flow in `test_competing_canonical_anchors_fail_closed_in_the_generic_resolver` (both passing, §7).
- **Transactional uniqueness: supported by code, not proven by tests.** The setter's `_write` runs eligibility SELECT → competitor clear → scoped UPDATE under `conn.execute("BEGIN IMMEDIATE")` on one connection, retried whole (re-read included) up to 3× on lock errors. Sequential last-writer-wins therefore converges to exactly one anchor per (project, setting) scope through this path.
- **Concurrent uniqueness: not proven.** Zero thread/concurrency tests in `test_generic_environment_canonical_authority.py` (`grep -c "thread|concurrent"` → 0). No concurrent-designation test exists anywhere for this setter.
- **Durable uniqueness: absent.** No UNIQUE index or partial unique index touches `reference_assets` (base table + 6 `ALTER TABLE … ADD COLUMN` migrations add `target_type/target_id/category/approval_state/canonical/source_kind` only). Out-of-band writers (raw SQL, future code paths) can reintroduce competing anchors. Mitigation verified in code: the resolver fails closed (`canonical_setting_reference_ambiguous`) instead of selecting. Do not claim concurrency safety.
- Additional note: the sync's `_sync_environment_canonical_flag` checks for competing anchors outside any transaction (read-then-write across separate storage calls), so a designation racing a sync could transiently produce two anchors — again contained by the fail-closed resolver, and covered sequentially by `test_sync_never_downgrades_or_competes_with_an_explicit_designation`.

## 6. Designation auditability (concern C)

`reference_assets` columns (base schema + migrations at `storage.py:1105`, `:3710`–`:3715`): `ref_id, project_id, kind, image_url, embedding, source_shot_id, created_at, target_type, target_id, category, approval_state, canonical, source_kind`. **No field records who designated a reference or when.** `created_at` records row creation, not designation; a designation flips `canonical` without touching any timestamp or actor column. The only when/which trace is operational, not durable: the `SETTING_REFERENCE_CANONICAL_DESIGNATED` log line (project/setting/ref_id, no actor). The R2.3 report's "state-only" characterization is confirmed. Whether the project requires per-actor traceability: the audit phases to date impose no such requirement (R2.2 asks only that designation be inspectable, which the canonical flag + `_approved_setting_references` satisfy), so this is a deferred hardening decision, not a defect — but any future claim of "auditable designation" must add persisted actor/timestamp fields first.
