## 2. Reproduced G1 defect and original evidence

R4.3D §9 G-1 (High): router jobs had no post-submission reconciliation. Re-verified against the current tree before editing:

- `RenderService.reconcile_completed_runway_task` (`render.py:5389`) early-returns for any `provider != "runway"` — failed router jobs with recorded task ids are never re-checked.
- `RunwayRouterAdapter.get_job_status` (`adapters/__init__.py:2772`) is a documented no-op ("the routed submit path polls to a terminal status inside submit_job"), so restart recovery's `adapter.get_job_status(job)` learns nothing for in-flight router jobs, which are then stale-marked failed.
- `RenderService.retry_job` (`render.py:5051`) re-submits the same durable row unconditionally (up to the cap), creating a new upstream task even when the recorded task may still be live.
- Reproduction as a failing test: `test_g1_blind_retry_is_blocked_after_ambiguous_timeout` (new file, §7) failed on current code — retry of a failed router job carrying a task id with an inconclusive lookup proceeded to a second adapter submit. After the fix it passes: `ValueError`, zero submits, zero POSTs.

Provider capability check (no invented capabilities): the router provider already performs `GET /v1/tasks/{id}` inside `_poll_runway_task` (`runway_router_provider.py:981`), so a single bounded task-status read uses a supported capability. No lookup-by-idempotency-key exists anywhere in the tree (confirmed by grep); the design therefore reconciles by recorded task id only, and blocks when no task id can be reconciled.

## 4. Implementation change

**`app/services/providers/runway_router_provider.py`** (additive only):

- New `fetch_runway_router_task_status(task_id, *, api_key=None)`: exactly one bounded `GET /v1/tasks/{id}` via the existing `_runway_router_request`; never submits, polls, sleeps, or retries. Missing key/task id raise `ValueError`; transport errors propagate for the caller to record as inconclusive.
- `submission_attempted: True` marker added to the two transport/parse/poll failure payloads (video + image submit) — i.e. precisely the failures that occur at/after the POST attempt. All pre-send failures (validation, incompatibility, missing key, conclusive 4xx rejections) are untouched, so non-creation stays established for them without any marker.

**`app/adapters/__init__.py`** (2 additive lines):

- `router_execution` now carries `submission_attempted` through from provider meta (explicit key, same pattern as all other execution evidence).
- `fetch_outputs` additionally accepts `association_source == "runway_router_reconciled_task"`; every identity check (task id, render job id, output URL, execution-equality) is unchanged.

**`app/services/render.py`** (all additive; no gate weakened, no check removed):

- `reconcile_runway_router_task(job_id)`: skips non-router/contract-only/complete/no-task-id jobs (no provider contact); otherwise one bounded lookup and exactly one of: adopt-as-complete (with output URL) through the three post-completion integrity reviews; preserve on upstream-active; fail with structured reason on upstream-terminal-failure (`retry_permitted: True` — the recorded task is dead); fail-closed block on inconclusive/unavailable/success-without-URL. Every path records `metadata["router_reconciliation"]` (`task_id`, `upstream_status`, `verdict`, `retry_permitted`, `detail`, `checked_at`) and persists. Upstream status taxonomy reuses the provider's canonical `_TASK_TERMINAL_SUCCESS` / `_TASK_TERMINAL_FAILURES` / `_TASK_IN_PROGRESS` (single source of truth, no duplicate).
- Adoption (`_adopt_reconciled_router_task`) mirrors the adapter's success record shape (normalized `provider_response_normalized` + `output_identity` with the reconciled association source), sets the existing `recovery_status="orphan_reconciled"`, and notifies — so delivery gates verify provenance identically to polled success.
- `_router_resubmit_decision(job)`: task id → reconcile, then adopted/proceed (upstream dead)/blocked; no task id → conclusive-rejection codes (`no_eligible_model`, `router_config_not_found`, `missing_runway_api_key`, `required_reference_incompatible`, pre-submit capability failure) proceed, `submission_attempted` without task id blocks, everything else proceeds unchanged.
- `submit_job`: single enforcement point — task-id-carrying failed/pending router jobs and marker-carrying failed jobs reconcile first; adopted returns the completed job, blocked restores `failed` with the blocking message and returns un-submitted (worker-safe: no raise, no new task). Initial submits (no task id, no marker) take zero extra calls.
- `retry_job`: after submit, a fresh blocked verdict raises `ValueError` (route → 409) instead of silently returning the un-submitted job.
- `retry_with_continuity_context`: reconciles ambiguous sources first; adopted returns the adopted job, blocked returns the source job with a refusal advisory and creates nothing.
- `recover_jobs_after_restart`: in-flight router jobs with task ids reconcile instead of the adapter no-op; failed router jobs with task ids join the orphan-reconcile branch; the complete-branch skips re-running reviews already applied by adoption (`reviews_applied` marker).

No new status names (all `recovery_status` values reused), no tables, no migrations, no public API fields (all evidence lives in established metadata dicts).

## 6. Duplicate prevention and concurrency guarantees

- Single enforcement point (`submit_job` gate) covers direct retry, continuity retry (additionally guarded pre-creation), queue re-dispatch, route resubmission, and restart recovery — verified by tests asserting zero transport POSTs and zero adapter submits on every ambiguous path.
- Adopted jobs become `complete`, so the existing terminal-state skip blocks all later submitters; blocked jobs stay `failed` with `retry_permitted: False` evidence, so every path re-blocks deterministically.
- Concurrent ambiguous retries each perform a read-only lookup (safe) and both block: proven by the `asyncio.gather` test (2 blocked, 0 submits, 0 POSTs).
- Residual (documented, not new): two concurrent retries that both observe a terminally-failed upstream task may each submit a replacement — but that is a legitimate new task, not a duplicate, and cross-process double-submit on the same row is a pre-existing characteristic of all retry paths, unchanged by this phase.

## 9. Remaining limitations and owner decisions

- No-task-id ambiguity cannot be reconciled (no lookup-by-idempotency-key capability exists — verified absent, not invented); it blocks with explicit-resolution guidance. If payment-coupled duplicate risk for this subclass needs a stronger answer, the decision is a provider capability question (idempotent submission support), not a code change to invent here.
- Dry-run-preflight transport failures carry the attempted marker although dry runs create no task — fail-closed over-block, documented; a phase-local marker refinement is possible follow-up, not required for safety.
- Reconcile-adopted outputs pass the standard post-completion reviews (per R4.3D §12.2's default); a different parity ruling would need an owner decision and is explicitly not changed here.
- R4.3D decision requests §12.1 (implement) is discharged by this phase; §12.3 (never auto-retry on ambiguity) is now enforced in code for all covered paths; §12.4 items remain open as before.
- Live provider behavior (billing, retention, real task lifecycle) remains unverified; mocked evidence only.
