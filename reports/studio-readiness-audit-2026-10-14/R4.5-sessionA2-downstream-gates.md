### 2a. How the Scene 002 path passes `mutable_render_input_mismatch` — and why a generic job cannot

**Answer: it does not, on the current tree.** There is exactly **one** place in
`create_job` that constructs a Router `RenderJobInput`, and both the Scene 002
(`execution_mode="SCENE_002_CONTRACT_ONLY"`) path and the generic path go
through it.

How the Scene 002 job's `RenderJobInput` is built and persisted:

- `SceneProductionPipelineService._submit_contract_only_batch`
  (`scene_production_pipeline_service.py:2320-2378`) calls
  `render_service.create_job(..., parameters=execution_parameters, generation_contract=…,
  prepared_generation_contract=…, execution_mode="SCENE_002_CONTRACT_ONLY", …)`.
  `execution_parameters` is `provider_input_parameters` merged with a fixed key
  list that **does** include `scene_coverage`, `scene_coverage_shot` and
  `dialogue_handoff` (`:2356-2368`).
- Inside `create_job`, the Router frozen branch (`render.py:2426-2548`) computes
  `frozen_parameters = dict(approved["creative_parameters"]) + duration /
  aspect_ratio / resolution / seed / content_moderation / reference_videos /
  reference_audio / keyframes / [storyboard]` (`render.py:2516-2533`) and builds
  `RenderJobInput(..., parameters=frozen_parameters, …)` (`render.py:2541-2548`).
  **The caller-supplied `parameters` are discarded here.** `create_job` returns
  this job (`:2648-2652`), so the durable row always carries
  `parameters == frozen_parameters` — for Scene 002 and generic jobs alike.
- The adapter compares the mutable inputs against the frozen proof
  (`adapters/__init__.py:2225-2236`):

  ```python
  if (job.input_payload.prompt != contract.prompt
      or list(job.input_payload.referenceAssets or []) != expected_reference_uris
      or params.get("scene_coverage")       != approved_coverage
      or params.get("scene_coverage_shot")  != contract.payload().get("scene_coverage_shot")
      or params.get("dialogue_handoff")     != contract.payload().get("dialogue_handoff")):
      return fail_contract("mutable_render_input_mismatch", …)
  ```

  `params` is `job.input_payload.parameters` (`adapters/__init__.py:2021`), i.e.
  `frozen_parameters`, which **never** contains those three keys.

**Evidence.** The freshly created jobs in the probe carry
`mutable_keys_absent_at_creation = [dialogue_handoff, scene_coverage, scene_coverage_shot]`
(both shots) and are refused `mutable_render_input_mismatch` on the first adapter
attempt. The session-A parity test documents the same gap and works around it by
patching the job's parameters after creation
(`tests/test_r45_shared_router_gates.py::test_parity_valid_artifact_agrees_everywhere`;
also `tests/test_generation_contract_remediation.py:730+`, which hand-sets
`scene_coverage` / `scene_coverage_shot` / `dialogue_handoff` on a hand-built
job before dispatch). Those hand-built/hand-patched jobs are the only artifacts
that pass this check today.

**Where the gap is.** `create_job`'s persistence projection (render.py:2516-2548),
not the pipeline and not the adapter. The pipeline *does* supply the correct
values (Scene 002 supplies them explicitly; the generic path supplies
`scene_coverage`/`scene_coverage_shot`/`dialogue_handoff` in
`generation_settings`, which create_job validates against the frozen contract at
`render.py:2302-2303`) and the adapter's expectation is the anti-tamper invariant
it exists to protect. Only the projection that decides *what gets stored* is
incomplete. Consequence: **no freshly created Router job — Scene 002 included —
can pass this check**; the pre-session-A caveat is therefore wider than
"generic jobs".

### 2b. The creative-parameters gate at `runway_router_provider.py:784`

`reconstruct_runway_router_video_request` ends its shared-value comparison with
(`runway_router_provider.py:784-785`):

```python
if payload["creative_parameters"]:
    raise ValueError("Runway Router cannot represent frozen creative parameters without loss")
```

What it compares: **truthiness of the frozen contract's `creative_parameters`
object.** Any non-empty dict is refused; it never reads the values.

Why the pipeline-built batch fails it: `freeze_generation_contract` writes the
shot's selection/coverage metadata into `creative_parameters`. The probe's two
pipeline contracts carry **nine** keys each: `character_focus`,
`character_focus_ids`, `content_coverage_disposition`, `content_coverage_reason`,
`covered_content_ids`, `creator_coverage_decisions`, `dialogue_disposition`,
`dialogue_disposition_reason`, `strict_render_settings`.

Which side is stale: the **upstream data shape**. The gate is correct for its own
invariant (the Router wire body has no field for these values, so forwarding them
would be lossy) and Checkpoint G's failure at the same line is the same artifact
class, not a stale fixture. The pipeline is what must change (freeze `{}` for
Router jobs, with selection metadata already carried by `scene_coverage`), **or**
the declared path must enforce an equivalent. Today the declared path neither
reads nor rejects `creative_parameters`
(`runway_reference_projection.reconstruct_projected_request:1301-1440` never
touches the field, and `build_runway_router_video_request` has no field for it),
so the probe's declared dispatch silently drops them while the unprojected path
fails closed — a **parity gap**, not a wire fix. Owner ruling:
`R4.5-gate-census.md` gate 9 (F8), still open.

### 2c. What the declaration gate reads, and what else reads that record

`adapters/__init__.py:2264` is the refusal
`reference_projection_declaration_missing`, raised when
`metadata["frozen_reference_binding"] is not None` and **neither**
`metadata["reference_projection"]` (`PROJECTION_METADATA_KEY`) **nor**
`metadata["reference_projection_authorization"]` (`AUTHORIZATION_METADATA_KEY`)
is declared (`adapters/__init__.py:2259-2266`; keys defined at
`runway_reference_projection.py:935-936`).

Fields read from the authorization record — `_declared_reference_projection`,
`adapters/__init__.py:1737-1812`, plus `authorize_environment_reference`,
`runway_reference_projection.py:962-1111`:

| Field | Requirement |
|---|---|
| `authorized_environment_ref_id` | non-empty string; must name the one canonical `setting` row (else `missing_reference_authority`) |
| `frozen_reference_binding` | must equal `metadata["frozen_reference_binding"]` exactly (else `reference_authorization_mismatch`) |
| `frozen_reference_binding_sha256` | must equal `reference_binding_digest(binding)` |
| `project_id` | must equal `creative_generation_identity.project_id` |
| `scene_id` | must equal `manifest.scene.scene_id` |
| `setting_id` | must equal the canonical setting row's `target_id` |
| `current_version_id`, `approved_version_id`, `storyboard_version_id` | all three mutually equal and equal to the manifest's storyboard version |
| `source_fingerprint` | non-empty, 64 lowercase hex; must equal the anchor row's computed fingerprint |
| `authorization_policy_id` | must equal `"runway_reference_projection_authorization"` |
| `rejected_environment_ref_ids` | must be a **non-empty `list`** — `[] or ()` collapses to `()`, which fails the `isinstance(…, list)` check (`runway_reference_projection.py:1023-1026`). Counter-intuitive but load-bearing |
| authorized row shape | `target_type="setting"`, `kind="environment"`, `canonical is True`, `approval_state="approved"`, `project_id` == auth `project_id`, `target_id` == auth `setting_id` |

Value derivation is then re-run through
`project_authorized_environment` (`runway_reference_projection.py:1112-1188`) and
`reconstruct_projected_request` (`:1301-1440`): exact replay of
`selected_ref_ids` / `omitted_ref_ids` / `studio_role_map` / `provider_role_map` /
`provider_uris` / `projection_digest`, `capacity == 4`, `projection_policy_id`,
policy version, and (for allowed local sources) `authorization_identity`
consistency; then the wire body is built by the existing Router builder and its
`referenceImages` are compared against the selected identities
(`adapters/__init__.py:1826-1836`).

What else reads the record:

- **Preflight** reads the *entry-level* authorization only for Scene 002
  (`scene_production_pipeline_service.py:954-966`: digest must equal
  `reference_binding_digest(binding)`). The generic `runway_router` branch
  (`:968-999`) never reads it — i.e. preflight neither requires nor mints a
  generic declaration. **This is the F5 seam.**
- **Creation** copies it into job metadata when the prepared entry carries one:
  `_batch_authorized_job_metadata` (`scene_production_pipeline_service.py:650-653`)
  and `:1934-1936`. Both are no-ops today because no generic entry ever carries
  one.
- **Retry/queue** carry the job's metadata unchanged.
- **Downstream (submit/reconcile/packaging/traceability)** nothing reads the
  authorization record itself after dispatch. What persists is the projection
  record mirrored into `job.metadata["router_execution"]`
  (`runway_reference_projection.router_execution_metadata:1463-1490`, written at
  `adapters/__init__.py:1855-1861`). Readers of `router_execution`:
  `render.py:5722-5797` (reconciliation / output identity),
  `adapters/__init__.py:2736-2744, 2798` (task id, output identity),
  `generation_cost_gate.py:215-216` (estimated-cost semantics),
  `scene002_contract_only.py:720,748` (result-only metadata allowlist). None of
  them re-verifies the declaration; the declaration is a **pre-dispatch** gate
  whose traceable residue is the mirrored `router_execution` block.

## 4. Revised F5 scope and effort

**F5 is one authority-minting change plus two data-shape prerequisites — not an
open-ended chase.** Evidence: after session A, exactly two refusals separate a
pipeline-built batch from mocked dispatch (#2, #3), and both are satisfiable by
data the test could construct. Nothing in the declared path required relaxing a
check, changing schema, or touching Scene 002.

Scope, in order:

1. **F7 (prerequisite, data shape, no auth semantics).** `create_job` persists
   the frozen `scene_coverage` / `scene_coverage_shot` / `dialogue_handoff` into
   `RenderJobInput.parameters` (or the adapter compares the frozen proof only).
   Without it, no freshly created job — Scene 002 included — passes gate #2, and
   every Scene 002 acceptance claim that relies on a fresh job is weak.
   *Decision required: store more (recommended) vs compare less.*
2. **F9 (new, data shape, no auth semantics).** Resolve the seed-lock / durable
   identity divergence so a job created with an unfrozen seed can still submit
   (freeze a seed at creation, or persist after the seed lock). Narrow, but it
   blocks the production entry before the adapter.
3. **F8 (parity, no auth semantics).** Router creative parameters: freeze `{}`
   for Router jobs (recommended) or enforce a `:784`-equivalent on the declared
   path. Checkpoint G's `:784` stop is this row.
4. **F5 proper (authorization semantics; owner decision 3).** Generic
   projection-authorization builder. It is a *builder*, not a new surface: the
   carrier already exists (`_batch_authorized_job_metadata`,
   `scene_production_pipeline_service.py:650-653`; preflight hook `:954-966`
   currently Scene-002-only), the record shape is fully pinned by §2c, and the
   consuming gate already accepts a conforming record (proven: both shots
   dispatched with zero check relaxations).

Effort: **one focused F5 session** for steps 1-4 plus record-shape negative
controls (unknown/garbage role, 5-ref batch, foreign `project_id`, tampered
binding, missing/stale authorization, `[]` vs non-empty
`rejected_environment_ref_ids`), then **one acceptance session** (T1 probe
conversion, T2 Checkpoint G rebuild, Runs 1-4 re-green). Confidence: **high**
for the F5 record shape (pinned by field and by a passing dispatch); **high** for
F7/F9/F8 as small, non-authorization data-shape changes; **medium** overall
because F7's direction and F9's resolution are owner decisions, and the measured
run is mocked, not live.
