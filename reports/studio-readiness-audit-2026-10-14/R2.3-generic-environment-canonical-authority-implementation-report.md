## 2. Root cause (from R2.2, confirmed during implementation)

Generic environment references had a verified *read* contract but no *write* contract:

1. The only generic path that set `canonical=True` was `sync_creator_references`, which wrote `target_id = scene_id` — an identity **no** production consumer accepts (all require `target_id == <canonical setting entity id>`). Those rows rendered as "Locked canonical" in Reference Space while authorizing nothing.
2. `POST /{project_id}/reference-assets` (`confirm`) persisted a client-supplied `canonical` value with no server-side check — an unaudited promotion path.
3. No parameterized designation operation existed; only the hard-coded Scene 002 pair (`project_5907c60cddbc` / `loc-c8f88b9c`) could be explicitly designated.

## 4. Resulting canonical designation contract and scope rules

- **Authority is conferred only by** `designate_setting_reference_canonical` (service), the new `…/canonical` route, or the creator approval the sync mirrors. `confirm` always persists `canonical=False`.
- **Eligibility:** project + setting must resolve through setting-identity provenance; row must be in that project, target exactly that setting entity, be `kind='environment'`, `approval_state='approved'`, and browser-usable. Rejected/candidate/unusable/foreign/wrong-kind/wrong-setting rows raise before any write, leaving existing authority untouched.
- **Exclusivity:** designation clears competing canonical anchors for the same setting in the same transaction. Two canonical anchors for one generic setting make resolution raise `canonical_setting_reference_ambiguous`; explicit designation is the resolution.
- **Scope fences:** blank identifiers rejected; the Scene 002 exact project/setting pair is refused by both the service and the route and keeps its own lifecycle.
- **Auditability:** designation is observable through existing state — `get_reference_asset` / `list_reference_assets` show the canonical flag, and `_approved_setting_references` shows exactly what the resolver will consume. No new audit subsystem was added (per scope).

## 5. Confirm endpoint handling of client-supplied canonical fields

`ReferenceAssetService.confirm()` still accepts the `canonical` field in the `ReferenceAsset` wire model (compatibility preserved — existing clients are not broken), but the value is **stripped server-side**: a supplied `canonical=true` is logged (`REFERENCE_ASSET_CANONICAL_CLIENT_SUPPLIED_IGNORED`) and the row is persisted `canonical=False`. Ordinary confirmation (proposal → approved row) is otherwise unchanged. Covered by a service-level test and a route-level test asserting `200` + `canonical: false` + a still-missing canonical anchor afterwards.

## 6. How synchronization now agrees with the production consumer

The sync resolves each scene's canonical setting entity via the same `resolve_canonical_setting_id` provenance the resolver uses and writes env-still rows with `target_id = <setting entity id>`, `target_type='setting'`, `kind='environment'`. Deterministic ref IDs (`_env_ref_id`) and the no-downgrade rule are preserved: re-sync upserts in place (no duplicates), never touches explicitly designated rows, and never revokes valid approved state. When no setting entity resolves, the sync keeps the historical scene-scoped row — production still fails closed for that scene at provenance, so the fallback authorizes nothing. Pinned by target-consistency, idempotency, fallback, and non-downgrade tests.

## 9. Remaining risks and unimplemented guarantees

1. **Durable uniqueness is transactional, not schematic.** Exclusivity is enforced by the setter's transaction; there is no DB-level partial unique index on `(project_id, target_id, canonical)` for setting/environment rows, so a concurrent or out-of-band writer could reintroduce competing anchors. The resolver fails closed if that happens (verified), but the invariant itself is not schema-hardened. No migration was introduced per scope; one may be justified later.
2. **Designation audit metadata is state-only.** Who designated and when is not recorded beyond the resulting row state; if per-actor audit is required, that is a deliberate follow-up, not something this phase claims.
3. **Frontend coverage is thin.** The designation action has API-client support and backend route tests but no new component test asserting the button's visibility rules; the existing 13 ReferenceSpace tests pass unchanged.
4. **Legacy scene-scoped rows still exist** where no setting entity resolves; they fail closed today, but a future cleanup could re-target or quarantine them explicitly.
