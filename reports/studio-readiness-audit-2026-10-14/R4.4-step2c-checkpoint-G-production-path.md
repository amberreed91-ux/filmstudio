## 2. How production builds the contract — the two paths compared

### 2a. The R3.3 router-reconstruction path (what actually reaches `:783` today)

R3.3's single-shot evidence that reaches `reconstruct_runway_router_video_request` is `tests/test_generation_contract_remediation.py::test_offline_router_reconstruction_matches_live_body_and_stale_script_fails_closed` (:413), driven by the hand-built `_job_with_frozen_contract()` (:30). Its sibling, `tests/test_runway_router_projection_integration.py::test_generic_four_projects_through_v2_to_mocked_provider` (:1196), never touches that function at all — it dispatches through the declared-projection path (`_declared_reference_projection` → `reconstruct_projected_request`) on a hand-built job carrying a hand-built authorization record.

The scaffolding is not the production shape. `_job_with_frozen_contract()`:

- synthesizes its own binding rows with `"role": "reference"` for every reference (:66–71), so `studio_role` is `reference` on all of them — not the `face`/`environment` roles the pipeline emits;
- **re-writes the manifest's `reference_binding` down to a 10-key projection that has no `project_id`** (:206–211) before fingerprinting;
- puts `frozen_reference_binding` only in `input_payload.parameters`, leaving job metadata free of `frozen_reference_binding`, so `_declared_reference_projection` is a no-op and `metadata.get("frozen_reference_binding") is None`, letting the submission fall through to `reconstruct_runway_router_video_request` (`app/adapters/__init__.py:2369`) and pass.

So the only contracts that pass `:783` are hand-shaped test scaffolding that has been post-processed to match the reconstruction's own projection. That is not evidence about pipeline-built contracts, and step 2a's inference from it was the weak link.

### 2b. The production (pipeline) path

1. Reference resolution — `reference_validation._approved_character_references` (:231) emits character rows with `role`/`category` = `face` (or `general`, `full_body`) and **no `project_id`**; `_approved_setting_references` (:329) emits setting rows with `role`/`category` = `environment` and **`"project_id": project_id` at :350**. This is intentional, documented production behavior.
2. Contract projection — `scene_production_pipeline_service._canonical_binding_to_contract_references` (:35–45) turns the raw binding into frozen contract references with `role="reference"` and `studio_role=<raw role>` (so `face`/`environment` survive into `studio_role`), and deliberately drops `project_id`.
3. Manifest — `shot_manifest.build_shot_manifest` (:159) copies the **raw** binding rows verbatim, `project_id` included.
4. Preflight — `generate_scene` (:387) → `preflight_batch_authorization` (:725). For `manifest_provider == "runway_router"` (:964) it mirrors the Router submit rules: `ROUTER_ROLES = {"reference", "storyboard", "storyboard_last"}` (:804) and rejects anything else as `unsupported_reference_role` (:984).
5. Creation — `render.RenderService.create_job` compares the manifest row against a contract-side projection with **no** `project_id` (`expected_binding`, :2468) and raises `"Frozen contract creative values do not match the manifest"` (:2538). Its earlier, provider-neutral check (`expected_manifest_reference_binding`, :2340–2366) *does* accept `project_id` (key included `if key in row`), which is why the simulated path is unaffected: the router-only block at :2418+ is skipped when `generation_contract is None`.
6. Adapter — `RunwayRouterAdapter._submit_job_after_authorization` requires a declared projection whenever a canonical binding exists (`reference_projection_declaration_missing`, `app/adapters/__init__.py:2264`), then applies the same role allowlist (:2307) and finally `reconstruct_runway_router_video_request` (:2369, with the `:744` projection, `:783` equality, `:788` role gate).
7. **The projection declaration is only ever built for one hardcoded pair** — `scene_production_pipeline_service.py:1530`: `if provider == "runway_router" and project_id == "project_5907c60cddbc" and scene_id == "scene_002"`. No generic project can ever receive one.

**What `:783` compares:** a 25-key `expected_values` projection of the frozen contract against the persisted manifest shot row, including `reference_binding` as an exact list-of-dicts equality; the contract side is projected to 10 keys with no `project_id` (`:744–756`). A pipeline-built contract therefore fails on the setting row (11 keys on the manifest side) and, if that were cleared, on the very next gate (`:786` allowlist / `:788` raise, `face`/`environment` not in `{"reference", "storyboard", "storyboard_last"}`). Pipeline-built contracts do **not** normally satisfy it.

## 4. Classification

**GENUINE DEFECT** — exactly the mission's second outcome: the pipeline-built contract fails at the project_id equality **and** at the role allowlist, for ordinary contracts produced by the real pipeline. Production cannot dispatch a setting-bearing, character-anchored multi-shot batch through the Runway Model Router. Four independent stops, all rejecting the same legitimate artifact:

1. `preflight_batch_authorization` → `unsupported_reference_role` (`scene_production_pipeline_service.py:984`, allowlist `:804`) — fires first; blocks `generate_scene` before any job exists.
2. `RenderService.create_job` router branch → `Frozen contract creative values do not match the manifest` (`render.py:2538` vs `:2468`) — same `project_id` shape divergence.
3. `reconstruct_runway_router_video_request` → `:783` (project_id equality), then `:788` (role allowlist).
4. Adapter → `reference_projection_declaration_missing` (`adapters/__init__.py:2264`) — unavoidable for generic projects, because the pipeline builds the required projection authorization only for `project_5907c60cddbc`/`scene_002` (`scene_production_pipeline_service.py:1530`).

The preflight's own invariant is also violated: its author comment promises it "applies them to the same frozen artifact — never stricter than submission, only earlier, so no valid batch can newly fail" (`scene_production_pipeline_service.py:801-802`), yet it mirrors the **unprojected** submit gates, which submission itself skips whenever a projection is declared — and no generic job can ever declare one. So the preflight gate is the reachable verdict, and it is the wrong one for the only batch shape the pipeline can build.

What this is **not**: it is not an authorization failure and not a safety regression. Every stop is fail-closed — zero jobs, zero provider contact, no silent substitution, no capacity trimming (2 refs ≤ 4, the R4.0A ceiling is untouched). Settled decisions D1–D3, G-5, G-6, R4.3L, R3.3 and the four-reference ceiling are not reopened: R3.3's single-shot generic v2 claim still holds, because that path dispatches through a declared projection on a hand-built job and never through `:783` on a pipeline-built one.

Step 2a's classification is therefore refuted in its safety assumption: "stale fixture" was only safe if a pipeline-built contract passes `:783`. It does not. Variant B would have converted the only multi-shot execute-path test into an assertion that the system correctly refuses something the brief requires it to be able to do, and the blocker on brief §11 criterion 1 would have been papered over.
