## 3. Confirmation data model and project/shot isolation

Table shot_reference_confirmations (migration 68): confirmation_id PK, project_id, scene_id, shot_id, confirmed_digest, status (default confirmed), created_at, updated_at; UNIQUE(project_id, shot_id); index (project_id, scene_id). One durable record per shot; re-confirming replaces the row (no history table — history is the job trail, unchanged).

Isolation: every read is scoped by (project_id, shot_id); a record stored under another project or shot surfaces as missing for the requested scope, which fails closed downstream. The write path stores server-resolved identity (project/scene/shot from the fresh binding, never client claims) and the authoritative digest. Client-supplied digests are compared, never persisted. Malformed stored digests can never equal a fresh digest, so they read as stale and block.

No first-class revocation subsystem was invented (per scope): invalidation is digest-mismatch-by-change — approvals or bindings change, the stored digest stops matching, status flips to stale, submission fails closed until a new explicit confirmation is recorded. This limitation is documented in section 9.

## 4. Persistence and recovery flow

Desk: Resolve (read-only binding + read-only record recovery) -> explicit Confirm (POST; server re-verifies, persists) -> durable record. Reload, navigate away/back, or reopen the project: Resolve re-fetches the record; recovered-confirmed renders only on backend-confirmed + digest match.

Previs: scene selection triggers listSceneReferenceConfirmations (read-only). Submit attaches the server-confirmed map only. Route-state handoff still travels and displays, but no longer sources submit digests — the server map does, so recovery works with zero route state.

## 5. Server-side revalidation path at submission

POST pipeline/generate -> generate_scene(require_persisted_confirmation=True) -> prepare/consume -> frozen-contract block (unchanged) -> preflight_batch_authorization with the flag -> per shot, after the existing digest-expectation check: load persisted digest; probe the current binding; missing persisted (with a resolvable binding) fails missing_confirmation; carried digest differing from persisted fails confirmation_mismatch; persisted failing verify_confirmed_binding fails stale/unresolvable with the existing verifier codes; unresolvable current binding with no record keeps pre-existing semantics (nothing confirmable; other checks decide), with a record it fails unresolvable. Then the unchanged R4.1A checks (blockers, manifest, currency, setting authority, projection policy) run. Any failure -> ValidationError(stage batch_authorization_preflight) with zero jobs; provider tripwires in tests prove no adapter is reached. Creation-time, submit-time, and adapter-level checks remain active downstream.

## 6. Stale and invalid handling

- No record -> missing (200 on GET; missing_confirmation at required submit).
- Record digest != current digest -> stale (tampered rows included: they can never match).
- Current binding unresolvable -> unverifiable on GET; unresolvable failure at required submit when a record exists.
- Cross-project/shot -> missing for the requested scope (scoped reads).
- Malformed row -> stale (never matches), fails closed.
- Carried digest != persisted digest -> confirmation_mismatch (client claims never override durable evidence).
- Frontend unknown (endpoint unavailable, still loading) -> no confirmed UI, Generate disabled whenever a confirmation is in play (carried or stale records present).

## 10. Remaining blockers, limitations, unverified claims

- SCENE_002_CONTRACT_ONLY protected execution returns before the batch preflight (pre-existing R4.1A structure) and keeps its authority-record flow; the require flag has no effect on that path. A future batch entrypoint that creates jobs without preflight_batch_authorization would bypass both R4.1A and R4.2 — the R4.1A grep-gate recommendation stands.
- No first-class revocation/expiry: invalidation is strictly digest-mismatch-by-change; there is no TTL, no explicit withdraw endpoint, no confirmation history.
- Shots with no resolvable current binding require no persisted confirmation (nothing confirmable); the remaining preflight checks decide. If a future policy wants confirmation for every shot regardless, that is a separate decision.
- GET scene recovery lists records by stored scene_id; shots whose scene_id changed since confirmation are recovered per-shot but may not appear in the old scene list (per-shot GET is the fallback).
- No live Runway verification and no end-to-end production-readiness claim; those are separate roadmap gates.
