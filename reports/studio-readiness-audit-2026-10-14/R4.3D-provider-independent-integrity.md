## 2. Architecture decision

Recorded as intended Studio architecture (authorization-relevant portions already enforced in code; failure-lifecycle portionsé aspirational — §5 marks each):

**A. Studio owns production truth.** Canonical truth = FilmLevelMemory, FilmStructure, CreativeSpine, explicit scene input, approved creator decisions. Providers and derived intelligence must not silently change identity, appearance, wardrobe, setting, dialogue, shot requirements, approved references, or creative decisions. *Status: enforced* — frozen-contract equality gates at creation/submit/adapter; canonical-model files contain zero `runway_router`/`ROUTER` references (verified by grep this phase).

**B. Studio owns production authorization.** The Production Integrity Gate is the final boundary; the Integrity Engine is advisory only. READY results, provider responses, HTTP statuses, and job ids are not independent authorization. All required checks fail closed at creation, submission, and adapter boundaries. *Status: enforced* — R4.1A/R4.2/R4.3A evidence re-confirmed (§8).

**C. Providers are replaceable execution systems.** Adapters implement a Studio-owned contract (`RenderProvider.render`, `providers/base.py:9`). Provider formats, capabilities, identifiers, and failure modes must not become canonical truth. Capability differences must be explicit; unsupported requirements are rejected or routed for creator decision, never silently removed. Runway remains the only approved production provider — no new integration, no live acceptance in this mission. The canonical model must avoid Runway-specific assumptions. *Status: partially enforced* — canonical model is provider-clean, but the pipeline mirrors one provider constraint (see §4 coupling point C-2).

**D. Failure is a first-class production outcome.** Every category in §5 must have a defined, evidenced behavior. A timeout never implies non-creation; ambiguous requests are never blindly resubmitted; retry requires reconciliation or idempotency evidence first. No automatic fallback, hidden ranking, silent substitution, or requirement weakening. *Status: incomplete* — the §9 G-1 gap.

**E. Preserve evidence across the lifecycle.** Studio must be able to state what was authorized, submitted, reported, received, and whether delivery satisfies requirements. No traceability claim without demonstrated linkage. *Status: established through delivery handoff; provider-side leg unverified* (§7).

**Already provider-independent (with evidence):**

- I-1 Canonical contracts carry no provider assumptions — `generation_contract.py`, `shot_manifest.py`, `scene_coverage_contract.py` contain zero router/Runway references (grep-verified). *Code-inspected.*
- I-2 Router resolution results (`resolved_model`, costs, settings) persist only as execution metadata (`router_execution`), never rewritten into canonical state (R4.3 §2 link 2–3, tested).
- I-3 No silent substitution anywhere: `select_provider_with_audit` returns `allowed=False` on mismatch (selection_audit.py); execution layer refuses silent mock substitution; `no_eligible_model` fails closed with no fallback (provider module + tests). *Tested.*
- I-4 Dry-run advisory discipline: `ADVISORY_ESTIMATE` semantics threaded from cost gate through adapter metadata; adapter comment at `:2483` states the dry run "is advisory, not authorization for the later live request." *Tested (mocked) + code-inspected.*
- I-5 Concrete-model prohibition at three layers (builder, `_validate_model_override`, adapter) — Studio never names a model on the router path. *Tested.*

**Remains provider-coupled (acknowledged, bounded):**

- C-1 The approved workflow supports exactly one production provider (`runway_router`); 13 other registry entries are non-production (simulated/local/training/disabled-direct). This is approved scope, not a defect — but "replaceable" is currently an architectural property, not a demonstrated one. *Unverified (no second production provider exists by design).*
- C-2 The shared pipeline preflight mirrors one provider's constraint: representable roles + `> ROUTER_CAPACITY` → `unsupported_reference_capacity` before any job is created (R4.1A check 6). Justified (fail-fast copy of the submit gate's exact rules applied to the submit gate's exact artifact), but it embeds a Runway number in shared pipeline code. If a future provider allows 6 references, this check must become capability-parameterized. *Tested; coupling documented, not removed (out of scope).*
- C-3 `router_execution` metadata shape (resolved_model/routing_provider/resolved_settings) is Runway-router-shaped execution evidence. Acceptable per decision C (execution metadata, not canonical truth), but a future provider needs its own execution-metadata shape, not a forced fit. *Code-inspected.*

No claim of universal interchangeability is made: capability differences (reference caps, roles, durations) are enforced as rejections, which is exactly what decision C requires.

## 10. Proposed next engineering change

**One change: router-aware reconciliation-before-retry (read-only provider read + adopt-or-fail, no auto-retry, no fallback).**

- Add a `reconcile_runway_router_task(job_id)` path that, for a router job carrying a `runway_task_id`, performs a single bounded `GET /v1/tasks/{id}` and either adopts a succeeded upstream task (attach output URL, mark complete through the existing integrity reviews) or records the verified upstream state (running → preserve; failed/absent → fail with structured reason). Wire it into exactly two call sites: the head of `retry_job` for router jobs with a task id, and the restart-recovery sweep alongside the existing direct-provider reconcile. No schema change (reuse `router_execution`/`recovery_status` metadata), no gate change (adopt still passes completeness + integrity reviews), no new provider, no live acceptance beyond what a future authorized task permits.
- Why smallest: it closes G-1's duplicate-task risk using only existing seams (task-id persistence, status-read adapter methods, reconcile outcome handling); it is verifiable with mocked provider tests (ambiguous-timeout → reconcile adopts; absent-task → structured failure; no second POST on retry-after-success).
- Why not implemented here: §7 forbids production-source edits without an explicitly authorizing task, and the change touches retry semantics — an authorization-adjacent behavior requiring owner approval (see §12). Tests would be: (1) timeout-after-submit records task id and fails; (2) retry reconciles first and adopts the succeeded task with zero additional POSTs; (3) reconcile of a dead task fails closed with the ambiguity recorded; (4) restart sweep covers router jobs; (5) all existing retry/reconcile suites unweakened.
