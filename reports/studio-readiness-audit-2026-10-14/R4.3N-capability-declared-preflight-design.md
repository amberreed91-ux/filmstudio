## 2. The existing capability mechanism (confirmed present, confirmed insufficient)

**There IS a capability declaration mechanism. It already carries reference
capacity. It does not cover the production provider.**

`studio-backend/app/services/provider_capability_contract.py` (471 lines):

- Declares `maximum_reference_images` plus evidence-gated
  `reference_conditioning` entries (`VERIFIED_LIVE` / `VERIFIED_CODE` /
  `UNVERIFIED` / `UNKNOWN`) — `:104-321`.
- `get_provider_capability()` returns a defensive copy; unknown providers get
  a fail-closed UNKNOWN declaration (`:324-352`) — Tested (23 tests in
  `app/services/test_provider_capability_contract.py`).
- `project_references_for_provider()` (`:361-429`) projects a selection into
  declared capacity — but its UNKNOWN/small-capacity mode **narrows to a
  single anchor and reports the rest as unconsumed**. That is correct for its
  advisory/reference-library context and **forbidden in the authorization
  path** (R4.0A no-silent-drop rule). The design must take the capacity
  NUMBER from this mechanism and keep Studio's REJECT semantics (§4).
- Precedent for capability-parameterized projection:
  `local_ltx_reference_projection.py:17-20` (declared capability const) and
  `:154-156` (capability-dict parameter) — Tested (17 tests).
- Precedent for per-provider evidence namespaces: `adapters/local_ltx.py`
  records `"provider_capacity": 1` under its own keys (grep-verified
  `:450,:549`) without colliding with `router_execution`.

**Why it cannot carry the change today (three gaps, all verified):**

1. **No `runway_router` row.** `_PROVIDERS` (`:314-321`) registers exactly
   six ids: `local_ltx`, `runway` (=1, direct-adapter path), `happyhorse-r2v`
   (=9), `minimax_h3_local`, `wan`, `comfyui_desktop`.
   `get_provider_capability("runway_router")` therefore returns UNKNOWN
   (fail-closed declaration) — Code-inspected.
2. **One production consumer, metadata-only.** The sole production caller is
   `render.py:1279-1280` (`_reference_debug`), which reads
   `reference_conditioning` for debug rows, never for authorization —
   Code-inspected. `project_references_for_provider` has zero production
   callers (tests only) — Code-inspected via caller search.
3. **The registry path is explicitly out.** `model_registry.py`
   (`ModelDefinition.maximum_reference_count`, `supports_reference_type`
   at `:100`) serves direct-model paths only; `render.py:1148-1156` states
   the router path "does not consult the registry (including
   `runway_router`…)" — Code-inspected. `providers/capabilities.py` covers
   only the legacy `mock`/`local_image`/`real_stub` seam with no capacity
   fields — Code-inspected. Neither is usable for R4.3N.

**Conclusion for §3:** no new abstraction layer is needed (per the owner
guardrail). The smallest design is one additive registry row + one narrow
preflight read — the existing adapter-and-contract architecture carries it.

   table untouched).

   change (verbatim rendering already correct, §1 #15).

   engineering change).

## 6. Analysis details (mission §3 c–g)

### 6.1 Preflight-from-capability with identical Runway behavior (mission c)

Preflight position is unchanged (post-frozen-contract block, pre-creation —
`:725+` flow per R4.1A §3), so the zero-job guarantee is structural, not
behavioral: same error code, same refusal point, same message intent (same
template, same interpolated `4`), same category. The F3 tests prove each
externally visible property.

### 6.2 No-capacity / different-capacity providers (mission d — analyze only)

- **Declares nothing (UNKNOWN):** in the capability contract's own advisory
  projection → single anchor + unconsumed report (never wired to auth, §4.3).
  In preflight under this design → fail-loud `ValidationError`, zero jobs,
  no provider contact. No silent narrowing is possible on either path.
- **Declares different capacity (e.g. 6):** preflight would compare against
  6 for that provider's entries; an over-capacity shot surfaces the same
  `unsupported_reference_capacity` code/category with the declared number in
  the message, zero jobs; the creator narrows the binding (narrowing UX
  remains the open R4.3-D3 product decision). No provider is enabled by this
  design, so this leg is analytic only — and R1 applies: submit/projection
  must be parameterized atomically before any such declaration ships.

### 6.3 Default-provider policy (mission e)

- **Legitimate mechanisms (not coupling):** `RENDER_VIDEO_PROVIDER` env →
  settings → default chain (`render.py:2042-2050`, retired/unknown rejected
  fail-closed, Tested); operator-alias resolvers
  (`scene_production_pipeline_service.py:2701-2714`,
  `previs_service.py:61-64`, both `"runway"`→`"runway_router"`,
  Tested) — they preserve creator intent, no authorization effect.
- **Demonstrated coupling, not authorization-affecting (C-4):**
  `config.py:29` (`render_video_provider = "runway"`); previs fallbacks
  (`previs_service.py:76-78`, `:220-227`); pipeline cost-gate allowance
  (`:1604` `(provider or "runway") == "runway_router"`); provider-branch
  literals (`:495,:514,:964,:1081,:1349,:1530,:1668,:2709`);
  `get_default_provider` consumers (`render.py:2208`,
  `generate_short_film_workflow_service.py:168`,
  `render_retry_service.py:1127`, `routes/projects.py:2643`). Each is
  defensible under single-approved-provider scope; collectively the "default"
  spells Runway. They select the path — the gates enforce regardless — so
  none affects authorization and none changes in R4.3N.

### 6.4 Per-provider evidence namespaces (mission f)

No collision demonstrated. `router_execution` (resolved_model, routing
provider/settings, `runway_task_id`, provider-passthrough
`capacity_fallback`) is router-shaped execution evidence under its own key;
`local_ltx` records `provider_capacity: 1` under its own keys (precedent for
divergence without collision); `generation_contract.py:30-35` carries a
neutral execution-metadata vocabulary. A second provider would add its own
keys under `metadata_json` (schemaless — no schema change). The one
namespace-adjacent item: Scene 002 authority records bind provider
`"runway_router"` + routing config (`scene002_contract_only.py:288`) — a
provider binding, not a capacity value; untouched by this design.

### 6.5 Frozen contracts and Scene 002 (mission g)

- **v1 contract path unaffected:** preflight's Scene 002 branch does
  digest-match only (~:948-963); F2 touches only the v2 branch. Existing v1
  suites (`test_scene002_contract_only`, composition-identity boundary)
  re-run unchanged.
- **`batch_authorization` stamp stores no capacity value** — verdict,
  `policy_version` label (`v1`/`v2`), digest, batch position
  (`_batch_authorized_job_metadata`, verified in `:620-669` window).
- **Stored strings embedding the number (informational, no gate reads
  them):** v1 `OMISSION_REASON_CODE =
  "capacity_4_of_5__lowest_identity_support_tier"`
  (`runway_reference_projection.py:70`) persists via projection records into
  job `reference_projection` metadata (`adapters/__init__.py:2603`); all
  located readers are pass-through/record-keeping (`adapters:1816`,
  `runway_ephemeral_upload.py:531,611,661`), and the projection digest does
  not cover the code string. v2's code (`within_capacity_no_omission`, `:71`)
  carries no number. Refusal message text (`(4 references)`) is never stored
  — refusals create zero jobs; the report is transient.
- **No stored frozen contract embeds the capacity value** (contracts carry
  references + digests, not the ceiling). No migration, no re-freeze, no
  Scene 002 authority change required.

## 8. Recommendation: implement AFTER R4.4 — defer, do not decline

- **The coupling is real and exactly what the owner named:** the ceiling lives
  in Studio's authorization contract (`:779`, `:990-994`), not only in the
  Runway projection. An over-capacity binding is legitimate under reference
  requirements (R4.0A §3) yet unauthorizable without editing shared pipeline
  code. This design is the right shape when onboarding arrives, and the
  existing capability contract (not a new layer) is the right carrier.
- **But nothing consumes it.** No second provider is approved (C-1 by
  design); the change is behavior-identical by construction, so its entire
  payoff is future option value. Landing it now on a 389-entry drifted tree
  (R-1) risks proving parity against the wrong baseline.
- **Higher-value work is queued.** R4.3K §10's legacy-previs alignment
  removes the last route-level Runway coupling with user-visible effect
  (previs usable with Runway unavailable) inside the same existing-contract
  discipline. It should go first; R4.3N follows after R4.4 re-baselining.
- **"Not at all" is rejected but bounded:** if single-provider scope ever
  becomes permanent policy, revisit — until then the design stands approved
  in shape, deferred in time.

**Stop conditions check:** the design requires no schema change, no
authorization-semantics change (same code/category/refusal/zero-job), no
stored-frozen-contract or Scene 002 v1 change, and no approved-workflow
change. No stop was triggered — but per mission §5, **no implementation
begins: awaiting owner approval.**
